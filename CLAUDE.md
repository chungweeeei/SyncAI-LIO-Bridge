# CLAUDE.md

The ROS 2 package `syncai_lio_bridge`, written in Rust (`rclrs` 0.8): the robot's only odometry
source and its localization provider. It turns the Point-LIO chain (`map → pointlio_odom →
pointlio_body`) into the planar `odom → base_link` TF, the `odom` topic and the AMCL-style
`map → odom` correction, all at 20 Hz. It is a port of
`~/Projects/SyncAI-Robot-Workspace/src/syncai_lio_bridge` (C++ / rclcpp), and **its external
interface must stay identical to the C++ version** (node name and executable `lio_bridge_node`,
`lio_bridge.launch.py`, parameter names, topics, frames, message types, QoS): the whole nav stack
depends on it. When behaviour is in doubt, the C++ version is authoritative; the README's
"Differences from the C++ version" lists every knowing deviation and must stay complete.

Its siblings are SyncAI-Robot-State and SyncAI-Robot-Driver-Manager (also Rust/rclrs), whose
layout and conventions this repo copies; `tf.rs` is shared with SyncAI-Robot-State almost verbatim.

**The repo root is the package itself** (`package.xml` and `Cargo.toml` are at the root); the
Workspace pulls it into `src/syncai_lio_bridge` with vcstool (replacing the C++ version).
`.devcontainer/` is only for developing this repo on its own. There is no Makefile,
docker-compose, params YAML or `interface.repos`: the launch file passes every parameter inline,
and the node uses only standard message packages.

## Build and test

Everything runs in the Dev Container `syncai-lio-bridge` (VS Code Reopen in Container, or
`devcontainer up --workspace-folder .`). The container's `/workspace` is the named volume
`syncai-lio-bridge_workspace` (holding build / install / log), and this repo is mounted at
`/workspace/src/syncai_lio_bridge`. The host has no ROS, so nothing can be compiled there —
`cargo fmt` is the only thing that works on the host, and `cargo check` fails in the `rclrs`
build script with "Failed to determine ROS distro".

```bash
docker exec syncai-lio-bridge bash -lc 'cd /workspace && colcon build --symlink-install --packages-select syncai_lio_bridge'
docker exec syncai-lio-bridge bash -lc 'cd /workspace/src/syncai_lio_bridge && cargo fmt --check'
docker exec syncai-lio-bridge bash -lc 'cd /workspace/src/syncai_lio_bridge && cargo clippy --target-dir /workspace/build/.clippy --all-targets'
docker exec syncai-lio-bridge bash -lc 'cd /workspace/src/syncai_lio_bridge && cargo test --target-dir /workspace/build/.clippy'
```

- `cargo` commands need one `colcon build` first: `/workspace/.cargo/config.toml` is generated by
  colcon-ros-cargo.
- Warnings from `/opt/ros2_rust_underlay/...` (rclrs itself) are not ours; ignore them. So are
  cargo's "Patch `<pkg>` was not used in the crate graph" notices — colcon-ros-cargo writes a patch
  entry per package on `AMENT_PREFIX_PATH`, and `ros-env` inlines message crates rather than
  depending on them.
- Before finishing, build / clippy / fmt must have zero warnings and all unit tests must pass.
- CI (`.github/workflows/ci.yml`) runs the same commands: `cargo fmt --check` on the bare runner,
  and `.github/scripts/ci.sh` (colcon build, `clippy -- -D warnings`, test) inside the Dev
  Container image built from `.devcontainer/Dockerfile`. Keep the script and this list in step.
- Without the Dev Container, any image that carries the ros2_rust underlay works the same way:
  mount an empty directory at `/workspace` and this repo at `/workspace/src/syncai_lio_bridge`,
  then run `bash /workspace/src/syncai_lio_bridge/.github/scripts/ci.sh`.

### Killing a test node

`pkill -f lio_bridge_node` run inside `docker exec ... bash -lc '...'` **kills the shell too**,
because the exec's own command line contains that string, and the whole script dies silently with
no output. Use `pkill -x lio_bridge_node` (matches the process name only). Note also that
`kill`ing the `ros2 run` wrapper leaves the node itself running — two stray nodes publishing at
20 Hz look exactly like one node at 40 Hz, and two nodes broadcasting `odom → base_link` fight
over the frame.

## Real-robot safety (important)

The dev container uses the host network and `ROS_DOMAIN_ID=2`, the same as the other dev
containers, so a node started here joins a graph that may include the real robot's. **This node
publishes `/tf`**: a copy started against the robot's domain broadcasts a second `odom →
base_link` and `map → odom` into the robot's TF tree and corrupts its localization. When testing
with fake `/tf` or `pointlio/lio_odom` publishers, `export ROS_DOMAIN_ID=77` so nothing here can
reach anything real (the real robot is domain 1).

## Architecture (`src/lio_bridge_node/`)

| File | Responsibility |
| --- | --- |
| `mod.rs` | Wiring: parameters → the two publishers → one worker → four subscriptions + one timer |
| `parameters.rs` | The six load-time parameters (all read-only), Hz -> period, seconds -> tolerance |
| `state.rs` | The worker payload: sample intake, the cached extrinsic, and the publish tick (`on_timer`) |
| `subscribers.rs` | The four subscriptions and their QoS; `geometry_msgs` -> `geometry` at the boundary |
| `geometry.rs` | **Pure** `Quaternion` / `Transform` / `Pose2D`, the `tf2` arithmetic; unit-tested |
| `tf.rs` | **Pure** TF buffer + lookup replacing `tf2_ros`; no ROS types, all unit-tested |
| `bridge.rs` | **Pure** `odom_to_base` and `map_to_odom`, the two formulas in the README; unit-tested |

New logic that can be expressed over plain Rust types goes in `geometry.rs` / `tf.rs` /
`bridge.rs` with unit tests; the ROS messages are converted at the subscription boundary so those
tests need neither a ROS environment nor the robot.

**Threading:** everything runs on ONE rclrs `Worker`, which is why there is no mutex anywhere.
Nothing blocks — the TF lookups are hash lookups in memory and the publishes are asynchronous — so
do not add a second worker without a blocking callback to justify it.

**The node hears its own `/tf` broadcasts**, like a `tf2_ros::TransformListener` would. They land
in the buffer and lengthen the chains (`base_link` acquires `odom` as parent) but never change a
lookup's answer; `tf.rs` has a test for exactly that.

## rclrs pitfalls (all hit in practice, here or in the sibling repos)

- **Worker = callback group**: callbacks from `node.create_*` all queue on the executor's single
  thread; callbacks from `worker.create_*` run on that worker's own thread. The callback shape is
  `FnMut(&mut Payload, Msg)`.
- **Timers default to steady time** (`TimerClock::SteadyTime`), i.e. `create_wall_timer`. Pass
  `.node_time()` only if the publish cadence should follow `/clock`; the stamps already do, because
  they come from `node.get_clock()`.
- **The log macros take `&Logger`, not `Logger`.** `log_warn!(self.logger, ..)` fails with
  "the trait `ToLogParams` is not implemented for `Logger`"; write `&self.logger`. A
  `self.logger.throttle(d)` argument already works, because the method call auto-refs.
- **`Arc::from(s)` in a parameter builder is ambiguous** when nothing downstream pins the element
  type — use `Arc::<str>::from(s)`.
- **No SIGINT handler**: Ctrl-C ends the process immediately and `Drop` does not run. A process
  backgrounded with `&` in a non-interactive shell script ignores SIGINT; send SIGTERM to stop it.
- **`ros-env` versions**: the package uses `ros-env` 0.2 while rclrs uses 0.3 internally, and their
  message types are incompatible. Do not use rclrs helpers that return message types (e.g.
  `Time::to_ros_msg`); `state.rs` builds the stamp from `Time::nsec`.
- The `Message` trait under `rclrs::*` is `rosidl_runtime_rs::Message`.
- Message packages do not go in `Cargo.toml` but in `<depend>` in `package.xml`; without it
  `ros_env::<pkg>` does not exist. Every generated message type implements `Default`, including
  the ones with 36-element covariance arrays.
- **A fresh image build can fail with "rustc 1.85.0 is not supported"**: rclrs commits no lock
  file, so its dependencies resolve to whatever is newest, and `uuid` already needs rustc 1.89.
  The Dockerfile sets `CARGO_RESOLVER_INCOMPATIBLE_RUST_VERSIONS=fallback` so cargo prefers
  versions whose `rust-version` fits the pinned toolchain. Do not "fix" this by bumping the pin
  alone: `clippy.toml` (`msrv`) and `rustfmt.toml` are written for 1.85.
- **`tf2_msgs` comes from the apt deb, not the underlay.** The official `ros-humble-*` interface
  debs ship generated Rust bindings at `share/<pkg>/rust`, and `tf2_msgs` is the one message
  package this node uses that the ros2_rust underlay does not rebuild and shadow.
- `launch/` is installed to share via `[package.metadata.ros] install_to_share` in `Cargo.toml`.

## Conventions

- Everything is written in English: code and config comments (Rust, Cargo.toml, Dockerfile,
  devcontainer.json, toml…), log messages, and docs such as README / CLAUDE.md. Log messages carry
  a `[Module]` prefix (`[LioBridge]`, `[Parameters]`), followed by the C++ node's own text so the
  README's diagnosis table still matches.
- Formatting follows the root `rustfmt.toml` (max_width 100); Cargo.toml enables
  `unsafe_code = "forbid"` and `clippy::all`.
- Commits use Conventional Commits (`.github/prompt/copilot-commit-message-instructions.md`), in
  English.
- The launch file is byte-for-byte the C++ package's apart from `lidar_frame`, which names
  `lidar_top_imu` (the lidar's IMU) since 2026-10 — the README's "Differences from the C++
  version" has why; a change to how `robot_id` is read belongs in both.
